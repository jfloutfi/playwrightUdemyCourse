Child Windows and New Tabs:
---------------------------

Playwright page context:
1) I open a page in a tab, I click on an element that has a link, I am taken to a new page in the same Tab. can I still use the same "page" variable?
=> YES

2) I open a page in a tab, I click on an element that has a link, I am taken to a new page in a bew Tab. can I still use the same "page" variable?
=> NO 

We need to capture the new page
we ALWAYS listen before we do an action that results in a Window or Tab:

This is bad:
await context.waitForEvent('page'); => we will get stuck here waiting
await page.locator('locator').click();

instead we use: Promise.all([...]);
const [newPage] = await Promise.all([
  context.waitForEvent('page'),
  page.locator('locator').click()
]);

it returns an array of promises, that is we capture in "const [newPage, ...]"
then, we start using "newPage.locator(...)"

NOTE: Promise.all() waits until every promise is fulfilled, or until one rejects.
More precisely:
  * ✅ If all promises resolve → Promise.all() resolves
  * ❌ If any promise rejects → Promise.all() immediately rejects
  * ⏳ Pending promises keep it pending
So it does not wait for promises to merely become “not pending”.

There is another one for dealing with "not-pending" state:
Promise.allSettled() => all settled (resolved/rejected) => never rejects

once we get what we need from the "newPage" and we need to flip back to the original page, we simply use "page" again

Route Matcher order
-------------------
page.route() handlers execute in reverse order of registration (LIFO — Last In, First Out)

await page.route('**/api/**', async route => {
  console.log('Handler A');
  await route.continue();
});

await page.route('**/api/content', async route => {
  console.log('Handler B');
  await route.continue();
});

=> we get in console "Handler B" because the 2nd one was registered last (like cypress)

BUT we also have route.fallback() to execute subsequent handlers:
await page.route('**/api/**', async route => {
  console.log('Handler A');
  await route.continue();
});

await page.route('**/api/content', async route => {
  console.log('Handler B');
  await route.fallback();
});

the output is 
Handler B
Handler A

route.fallback() passes control to the next matching handler after it (i.e the next matching one that was registered before the last matching one)

we can modify both the request and response, in this case, we use route.fetch() + route.fulfill()
fetch() allows us to also act on the request, .continue() in the other hand can't be used in this scenario bcz once route.continue() executes, Playwright sends the request to the server and relinquishes control of that route. You cannot subsequently call route.fulfill() on it.

It is the same with .fallback()
await page.route('**/api/**', async route => {
  const response = await route.fetch();
  await route.fallback(); // delegates the intercepted request to the next matching handler, or sends it to the network if no handler remains.
  await route.fulfill({ response }); // ❌ Invalid
});

By default, page.route() matches every request that satisfies its URL matcher, for as long as the route remains registered.
However, you can control how many times a route handler executes using the times option.

await page.route(
  '**/api/content',
  async route => {
    await route.fulfill({
      status: 200,
      json: { data: [] },
    });
  },
  { times: 3 }
);

You can also remove a route whenever you want:
await page.unroute('**/api/content', handler);

This requires importing the Route type: import type { Route } from '@playwright/test';

Playwright: Global API Routing with browserContext.route()
-----------------------------------------------------------
Use browserContext.route() to intercept API requests across all pages in a browser context. This is useful for redirecting requests to a different backend in CI/CD while allowing individual tests to mock specific responses.

await context.route(
  url => url.hostname === 'api.example.com',
  async route => {
    const url = new URL(route.request().url());

    if (process.env.CI) {
      url.hostname = 'api-ci.example.com';
    }

    await route.continue({ url: url.toString() });
  }
);

page.on('request', requestListener);

page.off('request', requestListener);

await page.removeAllListeners('request');

Fixtures
--------
different concept that cypress
not just .json files and saved data

when we define a test, we add {browser, page} => these are fixture already created by playwright
we can create our own custom fixture, for example: authenticated page
we add them in regular .js or .ts files

we need to tweek the "test" object behavior to handle custom fixtures:
import * as base from '@playwright/test';
// we need to export the definition so we can use it
exports.customTest = base.test.extend(
  authenticatedPage: async () => { // we can pass params here: async ({browser}, use)
    // write the code to login
    // then we add:
    await use(page) // final statement will be sent back or returned as the value of the fixture
  }
)

then the test suite file:
import authenticatedPage from 'the file where it is defined'
customTest('fixtures demo', async ({authenticatedPage}) => {
  authenticatedPage.goto(...)
})

playwright executes the authenticatedPage fixture 1st before entering the customTest block

we can extend with as many fixtures as we want. 1 thing: async ({...}, use) // "use" arg is mandatory

we can add alot of reusuable code to fixtures, for example: 
code that calls an API and returns an response or code that intercepts an API can returns a response, with "await use(myApiResponse)" as the final statement

fixtures can also be JS objects:
testDataForOrder: {
  someProductName: 'My Product',
  ...
}

fixtures support tear down as well:
...
await use(...)
// anything below here will be held off until the test using the fixture ends
// then the rest of the code here runs
we can use dispose methods like context.close() for example, to avoid leaks
