Await:
------
with playwright, we will need to use "await"
it is a bit closer to how javascript executes than Cypress, and does not have its own DSL schemes and so one,
so log term, it might be simpler to deal with that cypress, especially when it comes to commands, since in this case, they are just regular functions

when using "await", you need to make sure to designed the function as "async"

Playwright favors:

* Explicit flow
* No hidden magic
* Better debugging

Test and fixtures
-----------------
test('first playwright test', async ({browser}) => {}
browser is a fixture that availabe to all playwright tests
we must wrap it in {} else it will be treated like som regular string variable

test('first playwright test', async ({browser}) => {
    // chrome - plugings, cookies... etc
    // newContext => opens a fresh browser instance
    // we can use this method to inject cookies for example, basically configure the browser as it launches
    // this can help establish sessions the same it is done in cypress so avoid re-logins
    const context = await browser.newContext();
    const page = await context.newPage();
    await page.goto('https://somehost.com');
});

we can also use ({browser, page}) or just ({page})
using "page", playwright will create for us default browser, context... etc

await page.locator('[style*="block"]').textContent();
=> extracts text content found in element matched via locator

Consider:
1- const text:string|null = await page.locator('[style*="block"]').textContent();
   expect(text).toContain('Incorrect');

2- await expect(page.locator('[style*="block"]')).toContainText('Incorrect');

3- expect(await page.locator('[style*="block"]')).toContainText('Incorrect');

The correct one is "2", bcz toContainText() is the method that returns the promise
in "1", the value might end up as null and there will be no retries, in this case, these happen on "expect"
"3" is a bug, locator does not return a promise

IMPORTANT: Auto-wait
--------------------
not all playwright methods have auto-wait, also the nature of the waits can be different
refer to the following documentation page for this information: https://playwright.dev/docs/actionability

for example, this method: .allTextContents() => fetch all text from multiple results that are fecthed by 1 locator does not wait until all the text is loaded, so we would need to implements waits, the best way would be smart waits:

Smart waits
-----------
await page.waitForLoadState('networkidle');
=> playwright will wait for all the network calls are made to continue, i.e once the network stops registering calls
based on official playwright docs, this wait can be flaky
so another way to wait would be to wait on the locator itself: await page.locator('xyz').waitFor();
however, waitFor() work only when the locator returns a single element

Child Windows and New Tabs:
---------------------------

Playwright page context:
1) I open a page in a tab, I click on an element that has a link, I am taken to a new page in the same Tab. can I still use the same "page" variable?
=> YES

2) I open a page in a tab, I click on an element that has a link, I am taken to a new page in a bew Tab. can I still use the same "page" variable?
=> NO 

We need to capture the new page
we ALWAYS listen before we do an action that results in a Window or Tab:

This is bad:
await context.waitForEvent('page'); => we will get stuck here waiting
await page.locator('locator').click();

instead we use: Promise.all([...]);
const [newPage] = await Promise.all([
  context.waitForEvent('page'),
  page.locator('locator').click()
]);

it returns an array of promises, that is we capture in "const [newPage, ...]"
then, we start using "newPage.locator(...)"

NOTE: Promise.all() waits until every promise is fulfilled, or until one rejects.
More precisely:
  * ✅ If all promises resolve → Promise.all() resolves
  * ❌ If any promise rejects → Promise.all() immediately rejects
  * ⏳ Pending promises keep it pending
So it does not wait for promises to merely become “not pending”.

There is another one for dealing with "not-pending" state:
Promise.allSettled() => all settled (resolved/rejected) => never rejects

once we get what we need from the "newPage" and we need to flip back to the original page, we simply use "page" again

Locators Capturing multiple elements
------------------------------------
Say we are looping of a list of elements to find one:
for(...) {

              so we break from the look as we have achieved what we needed
  }
}

---- Sudo Class locator: ----
say we are using the tag name to find an element:
page.locator('h3'), we can do page.locator('h3:has-text("bla bla")')

.isVisible(); => returns true: checks if element is visible on the page
then, we would need to check the bool value if it is toBeTruthy
we can also use: await expect(page.locator('h3:has-text("bla bla")')).toBeVisible()

---- A better way to write the above: ----
await expect(
  page.locator('h3').filter({ hasText: 'bla bla' })
).toBeVisible();

or:

await expect(
  page.getByRole('heading', { name: 'bla bla' })
).toBeVisible();

if we want to use the .isVisible() check, we can locate the parent element and use .waitFor()

Autosuggestions when typing in a box
------------------------------------
we use .pressSequentially() instead of fill()

for loops and awaits
--------------------
iterating over a table rquires getting the rows and the row count:

Note: we might need to wait for the table to load 1st: await page.locator("tbody").waitFor();

cost rows = await page.locator("some locator");
const rowCount = await rows.count(); // better to get the count 1 time before the for loop
for (let i = 0; i < rowCount; i++) {
  if (someId.includes(someOtherId)) {
    await rows.nth(i).locator("someButton").click();
    break;
  }
}

Note: .count() returns a Promise<number>, thus the await is needed

An even more Playwright-ish approach is to use all() if you want to iterate over the locators:

const rows = await page.locator('some locator').all();
for (const row of rows) {
  console.log(await row.textContent());
}
